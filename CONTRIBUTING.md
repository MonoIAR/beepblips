# Contributing to beepblips

Thanks for taking a look. This is a small, zero-dependency project — the whole
engine is one file — so the contribution loop is short.

## What you need

- Node.js 22 or newer. CI runs the suite on 22, 24 and 26.
- That's it. There is nothing to install: `npm install` has no packages to fetch
  and no build step to run before the tests.

## Layout

| Path | What lives there |
| --- | --- |
| `beepblips.js` | The library: text analysis, prosody, synthesis, WAV encoding. |
| `cli.mjs` | The `beepblips` command-line wrapper. |
| `build.mjs` | Inlines `beepblips.js` into `index.html` between the marker comments. |
| `index.html` | The demo page, and the file GitHub Pages serves. |
| `test/*.test.js` | The `node --test` suite, one file per behaviour area. |

## The loop

1. Fork and branch (`fix/pinyin-tone`, `feat/voice-preset`).
2. Make the change.
3. `npm test`
4. If you touched `beepblips.js`, run `node build.mjs` so the demo page picks up
   the new engine, then `node build.mjs --check` — that sync check is what CI
   enforces.
5. Open a pull request using the template.

## Ground rules

- **No runtime dependencies.** The engine has to keep working when the file is
  copied next to someone's code, loaded from a `<script type="module">`, or run
  in a web worker. A new dependency would need a very good reason.
- **The engine stays I/O-free.** No `window`, `document`, `fs`, `fetch`, timers
  or `AudioContext` inside `beepblips.js`; the demo page and the CLI own that.
- **Determinism.** Same text, same options, same seed → same samples. Changing
  audio behaviour means updating or adding tests.
- **House style.** Two-space indent, single quotes, semicolons, LF line endings
  (`.editorconfig` and `.gitattributes` handle the mechanical part). Comments may
  be Chinese or English; public documentation is English, with the Chinese README
  (`docs/README.zh.md`) kept as a translation rather than a second source of truth.
- **Demo page.** Edit `index.html` outside the `beepblips:begin` /
  `beepblips:end` markers only; the text between them is generated by
  `build.mjs`.

## Tests

Each file in `test/` mirrors one area of the engine. A bug fix should come with a
test that fails before the fix; a new option should come with a test that pins its
default and its documented effect.

## Commits

History uses the `feat:`, `fix:`, `docs:`, `ci:` and `chore:` prefixes with an
imperative subject. Keep a pull request to one topic.

## Releasing

Releases are tag-driven and published from CI:

1. Bump `version` in `package.json`.
2. Commit, then tag: `git tag -a vX.Y.Z -m "beepblips X.Y.Z"`.
3. Push the commit and the tag, then publish a GitHub release for it.
4. Publishing the release triggers `.github/workflows/publish.yml`, which tests,
   verifies that `index.html` is in sync, and runs `npm publish --provenance`
   through npm Trusted Publishing.

## Security

Please do not report security problems in a public issue — see
[SECURITY.md](SECURITY.md).
